# School MIS: production readiness and completion plan

Audit date: 18 October 2026. Scope: the complete school web product, excluding payment gateway integration. This audit examines source code, the approved product plan, current migration contracts, regression tests and the connected project's advisors. It is not a claim that every route or deployment scenario has been tested during this audit.

## Current conclusion

The product is a functioning Supabase-backed development workspace with extensive screens and five verified cloud roles. It is **not yet an end-to-end production school system**. Persisting a form and moving its status is not equivalent to completing its downstream business workflow. The earlier 82 automated tests, 55 live integration checks and 17 browser checks prove selected scenarios, not all modules or safe live-school deployment.

Target users and feature scope remain those approved in `end-to-end-product-plan.md`. Keep the current Next.js application, supplied design system, feature folders and shared schema-derived models. No new competitor research or visual redesign is needed for this completion pass.

## Architecture and database completion

Keep the approved modular monolith. Each feature should follow:

`screen → verified identity and active membership → permission check → request schema → domain command → transaction + audit/outbox → permitted response projection`.

Use `src/features/<module>/{schemas,models,domain,data,server,components}` and reuse exact shared schema imports. Server-side responses remain unknown until parsed. The current canonical models should not be duplicated into a second unrelated database vocabulary.

Incremental table families: membership roles/permissions and active context; conversations/participants/messages; private document records; feature-owned attendance/marks/fee/operational tables; publication versions; audit/outbox/job attempts. Use school/year-scoped relationships and explicit restricted-data policies. Add indexes to the actual list/lookup/worker paths and test row-policy denial, not merely successful admin queries. Do not treat a privileged server key as authorization.

Preserve the current validated workspace through incremental migration/backfill with count/balance reconciliation, a rollback snapshot and read parity checks. Avoid a one-shot rewrite or replacing existing data with fresh workspace seeds.

## API and screen completion

Next.js Server Actions are a valid interface; a new REST framework is not required. Replace full-document mutations with small feature contracts: invite/assign/revoke; upload/finalize/download; send/acknowledge; approve/reject/post/reverse; issue/return/receive; publish/revoke; enqueue/retry/cancel. Responses should distinguish validation, forbidden, stale revision, provider unavailable and retryable failure without exposing secrets or raw database details.

Retain the existing Figma-based layout and design tokens. Complete actual workflows and their loading, empty, permission, error, retry and success states before adding decorative pages. Rename or remove simulation claims when a real path is complete; hide unsupported actions in live mode instead of implying they work.

## Delivery sequence and acceptance gates

1. **Security and access foundations** — patch reproduced gaps; finish permission and membership design; tests for every role and restricted record; separate workspace access. Acceptance: no cross-person/thread/school access, no privilege escalation or archive loss.
2. **All school roles and document storage** — complete specialist cloud adapters and private bytes; configure invitation/recovery paths. Acceptance: every role can complete its permitted daily workflow from another browser, including private file download and revocation.
3. **Messaging and background work** — real in-app conversations plus selected external channels, durable outbox/jobs and report publication. Acceptance: messages/jobs complete with browsers closed and duplicates/retries do not duplicate effects.
4. **Business workflow completion** — admissions/enrolment, attendance, teaching/exams, offline finance, HR, library, inventory, hostel, activities, health, front office, CMS and year-end. Acceptance: each intake/approval/action produces the expected downstream records, balances/history and permitted portal views.
5. **Production and launch verification** — staged data import, CI/E2E, performance/concurrency checks, monitoring, backups/restore and school-user acceptance. Acceptance: a full academic lifecycle can be exercised with recoverable failures; real-school deployment configuration is reviewed.

These are engineering milestones, not claimed completion or a reliable calendar estimate. Estimate duration after the role/tenancy decisions, provider choices, school policies and acceptance datasets are confirmed.

## External configuration needed later

Production domain/hosting; email sender/SMTP or provider access; optional SMS/WhatsApp/Push accounts and approved templates; real school roles/policies, document samples and payroll/report rules; storage/backup requirements. GPS/biometric/board/accounting connectors require actual providers/devices if included. **Payment gateway credentials are explicitly excluded.** Missing credentials do not block internal modeling, permission fixes, private storage wiring or repeatable tests.
